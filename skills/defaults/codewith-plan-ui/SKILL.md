CodeWith 계획서의 UI는 서버의 공통 템플릿으로 렌더링한다. 임의의 전체 HTML이나 CSS 테마를 만들지 않는다.
스펙 선택은 `스펙 번호 (스펙 제목)` 형식의 탭/메뉴, 본문은 요구사항 제목과 다음 고정 순서로 구성한다.
01 구현 방법 → 02 BEFORE / AFTER (두 패널, 좁은 화면에서는 세로 배치) → 03 UI 목업 → 04 DB 변경 → 05 검증.
각 섹션은 동일한 둥근 카드, 여백, 제목 단계와 코드 블록 스타일을 사용한다. 색상·글자 크기·여백은 앱의 공통 테마와 렌더러가 정한다. 모델이 색상·CSS·폰트·페이지 레이아웃을 재정의하지 않는다.
생성 응답 files의 각 content는 JSON 객체로 직접 작성한다. JSON 문자열로 이중 직렬화하지 않는다. 현재 실행의 응답 스키마를 우선한다. 필드는 implementation, before, after, ui, mockup, database, verification이며 모두 문자열이다. mockup만 독립된 HTML/CSS 화면 조각이고 나머지는 Markdown 본문이다. 코드에는 언어가 있는 코드 펜스를 사용한다.
UI가 없다면 ui에 해당 없음과 이유를 적고 mockup은 빈 문자열로 둔다. 목업은 계획서 바깥 테마를 바꾸지 않으며 별도의 격리 영역에 렌더링된다. 목업 안에서도 기본 서체와 둥근 입력칸·버튼을 사용한다. 외부 리소스나 스크립트를 넣지 않는다.
수정 요청 시 내용만 바꾸고 섹션 순서와 표기, BEFORE/AFTER 레이아웃을 유지한다. 일반 채팅에서는 이 템플릿을 설명할 수 있으나 계획 생성 API가 아닌 대화에 파일 생성을 요구하지 않는다.

새 탭 검토 화면의 단계는 위 다섯 섹션에 대응한다. 섹션을 합치거나 제목만 남기지 않고 각각 독립적으로 검토할 본문을 제공한다. 단계 승인·수정 요청·전체 승인과 편집 도구는 앱이 삽입하며, 생성 HTML에 별도 버튼 스크립트·승인 상태·점수를 만들어 넣지 않는다. 사용자의 편집본을 다시 생성할 때 내용과 코드 언어 정보를 보존한다.

## 사람이 읽고 검토하는 문서

- 계획서는 사람과 AI가 결정을 검토하고 의견을 주고받는 문서다. 각 섹션은 목적·변경점·선택 이유를 짧게 설명한 뒤 필요한 상세 내용을 제공한다. 요약은 전체 적용 코드를 대신하지 않는다.
- 비교·계약·검증 항목은 제목이 있는 Markdown 표로 정리한다. 한 셀에 긴 코드나 여러 논점을 몰아넣지 않고 상세 코드와 설명은 표 밖에 둔다. 관련 없는 정보를 한 표에 합치지 않는다.
- 확인할 항목은 `- [ ] 확인할 내용` 형식으로 작성한다. 근거가 있는 실제 완료만 `- [x]`로 표시한다. 사람이 체크할 수 있는 컨트롤과 저장은 앱이 제공한다. 체크 여부는 검토 표시이며 테스트 통과나 최종 승인과 구분한다.
- 평가 지적에 대한 사람의 의견·이견이 전달되면 근거와 함께 검토하고 수용·미수용 이유를 설명한다. 의견이 있다는 이유로 지적을 자동 해소하거나 승인됐다고 취급하지 않는다. 현재 편집 내용과 체크 상태를 관련 없는 변경으로 초기화하지 않는다.

## 섹션별 표현 계약

| 섹션           | 처음 보여줄 내용              | 상세 표현                                                                                                 |
| -------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| 구현 방법      | 목적·주요 변경·결정 이유      | `대상 파일 / 변경 내용 / 이유` 표와 순서 목록. 대안은 장단점을 비교한다.                                  |
| BEFORE / AFTER | 파일 경로·생성/수정/삭제 구분 | 언어가 지정된 전체 코드. 여러 파일은 파일별 소제목으로 구분하며 큰 코드를 표 셀에 넣지 않는다.            |
| UI 목업        | 사용자 흐름·주요 상호작용     | 목업과 빈 상태·오류·로딩 동작. 관련이 없으면 이유를 명시한다.                                             |
| DB 변경        | 영향·호환성·복구 방법         | 변경 비교표와 전체 DDL/마이그레이션 코드. 관련이 없으면 이유를 명시한다.                                  |
| 검증           | 확인할 완료 기준              | `완료 기준 / 확인 방법 / 기대 결과` 표와 실제 체크 가능한 `- [ ]` 목록. 실행 전/미검증을 명확히 구분한다. |

표에는 헤더를 두고 하나의 행은 하나의 비교 항목을 나타낸다. 셀에 문단을 쌓지 않으며 설명·코드는 표 다음에 둔다. 체크 항목은 각각 독립적으로 판단할 수 있도록 작성한다. 예:

```markdown
| 완료 기준           | 확인 방법              | 기대 결과                         |
| ------------------- | ---------------------- | --------------------------------- |
| AC-1 중복 요청 방지 | 같은 입력을 두 번 요청 | 두 번째 요청이 명시된 오류로 종료 |

- [ ] AC-1의 정상·중복 요청 결과 확인
- [ ] 오류 안내 문구와 복구 동작 확인
```

## 사람과 AI의 검토 흐름

좌측 검토 메뉴는 버전·저장 상태·평가 지적·사람의 의견·AI 수정·최종 승인·스펙 선택을 하나의 흐름으로 제공한다. 메뉴는 접을 수 있고 본문은 오른쪽 화면을 넓게 사용한다. 모바일에서는 메뉴를 필요할 때만 연다. 이 UI와 실제 체크 상태 저장은 앱이 관리하며 모델은 가짜 버튼·체크박스 문자·승인 결과를 출력하지 않는다. 단계별 의견은 해당 단계에, 평가에 대한 이견은 해당 지적에 연결한다. 의견의 작성자·내용·근거를 보존하고, AI는 요청된 수정의 반영 여부를 설명한다. 지적의 해소 여부와 사람의 최종 승인은 별개다.
